- [x] **Phase 1 (done) — interview_qa extraction.** Port `hrb_chatbot_v2`'s `interview_qa_store.py` + the `/interview-qa` routes from `manage_admin.py`. Behavior must not change - ported tests pass unmodified.
  - **Spec:**
    - **Context:** first of three admin/platform capabilities being extracted out of `hrb_chatbot_v2` into this repo (Phase 0 confirmed standalone deployment). Interview Q&A is a self-contained Postgres-backed CRUD resource with no dependency on RAG pipeline code, making it the simplest of the three to extract first.
    - **Source:** `hrb_chatbot_v2`'s `src/hrb_chatbot/common/clients/db_client/interview_qa_store.py` (store + SQL), `src/hrb_chatbot/models/interview_qa.py` (Pydantic models, ported as-is), and the 5 `/interview-qa*` routes at `src/hrb_chatbot/api/admin/manage_admin.py` lines ~774-821. Route-level test behavior ported from `tests/hrb_chatbot/api/admin/test_manage_admin.py`'s interview-qa tests, using the same `FakeInterviewQaStore` shape already defined in that repo's `tests/conftest.py` (lines 982-1043).
    - **API surface:** `src/platform/interview_qa/models.py` - `UserProfile` (minimal local copy: `employee_id`/`full_name`/`role`/`department`, no role enforcement - see Out of scope), `KeywordEntry`, `FeatureReference`, `InterviewQaCardFields`, `InterviewQaCard`, `InterviewQaListResponse`, `CreateInterviewQaRequest`, `UpdateInterviewQaRequest`, `DeleteInterviewQaResponse` - all ported as-is from `models/interview_qa.py`. `src/platform/interview_qa/store.py` - `InterviewQaStore` class, same CRUD methods (`list_cards`/`get_card`/`create_card`/`update_card`/`delete_card`/`health_check`), same table/SQL. `src/platform/interview_qa/routes.py` - `APIRouter` with `GET /interview-qa`, `GET /interview-qa/{card_id}`, `POST /interview-qa`, `PUT /interview-qa/{card_id}`, `DELETE /interview-qa/{card_id}`, same paths/methods/response shapes/status codes (200/404) as the original. `src/platform/common/responses.py` (`json_error`) and `src/platform/common/error_codes.py` (`INTERVIEW_QA_NOT_FOUND`) - small shared helpers, not business logic, usable by later phases too. `src/platform/main.py` - new FastAPI app entrypoint (didn't exist yet despite `CLAUDE.md`'s own run command referencing it), includes `interview_qa`'s router.
    - **Connection-plumbing adaptation (the one place real logic changes, not a straight port):** the original gets its connection through `hrb_chatbot_v2`'s own `read_setting`/raw `psycopg.connect(...)` called directly in the store. This repo has no `db_gateway`/`postgres_client` abstraction, so `InterviewQaStore._connect()` is rewired to call `hrb_common.db.connection.get_connection(config)` with a `hrb_common.db.connection.PostgresConnectionConfig` built from env (via that module's own `read_secret`-based `.from_env()`) instead of reading settings itself. The actual SQL/CRUD logic (table DDL, column lists, parameterized queries) is unchanged.
    - **Behavior parity:** the 4 non-RBAC-specific tests from `test_manage_admin.py`'s interview-qa block are ported and must pass: list filtered by topic, get-404-for-unknown-id, create+update+delete round trip, update-404-for-unknown-id. `test_employee_admin_cannot_list_interview_qa_cards` (403 for wrong role) is **not** ported - it tests RBAC middleware (`require_role`/`Role.ADMIN`) that doesn't exist in this repo (see Out of scope).
    - **Out of scope:** no RBAC/gateway layer invented as a side effect. Confirmed `src/platform/main.py` doesn't exist yet and there's no existing identity/role-check mechanism anywhere in this repo. All 5 routes accept requests with no identity check for now - `UserProfile` stays in `Create`/`UpdateInterviewQaRequest` bodies only for wire-shape parity with the original models (ported as-is per the brief), but nothing reads or enforces its `role` field. The original GET routes' query-param identity (`identity_from_query_params`, Phase 96 in `hrb_chatbot_v2`) is dropped entirely rather than ported as a dead parameter, since there's no role check behind it to perform and no `models/common.py`/`IdentityPayload` in this repo's scope.
    - **Open questions:** none blocking - flagged in the delivery note instead: (1) no RBAC layer exists here at all, so these admin routes are currently open to any caller; (2) `src/platform/main.py` didn't exist before this phase, created here as minimal scaffolding.

- [x] **Phase 2 (done) — build_deployment extraction.** Port the CI/CD pipeline dashboard routes (`pipeline_run_store.py`, `eval_run_store.py`, `golden_dataset_store.py` and their routes).
  - **Spec:**
    - **Context:** second of three admin/platform capabilities extracted out of `hrb_chatbot_v2` (Phase 1's interview_qa pattern - connection-plumbing swap, no RBAC - carries over directly). This one is bigger: 3 Postgres stores plus a real GitHub Actions dependency and genuine multi-repo/multi-workflow routing logic (`Application` enum: backend/ingestion_lambda/lms_mcp/frontend), not just CRUD.
    - **Source:** `hrb_chatbot_v2`'s `src/hrb_chatbot/common/clients/db_client/{pipeline_run_store,eval_run_store,golden_dataset_store}.py` (stores), `src/hrb_chatbot/models/admin.py` (only the models these 7 routes need - `GoldenDatasetCaseSummary`/`GoldenDatasetListResponse`, `EvalRunSummary`/`EvalRunListResponse`/`EvalRunCaseDetail`/`EvalRunDetail`, `WorkflowRunSummary`/`WorkflowStatus`/`CiStatusResponse`, `PipelineStepDetail`/`PipelineJobDetail`/`PipelineWorkflowRun`/`PipelineStatusResponse`, `PipelineSnapshotSummary`/`PipelineSnapshotListResponse`), `src/hrb_chatbot/common/enums.py`'s `Application` StrEnum, and the 7 routes + the `_to_workflow_status`/`_APPLICATION_REPOS`/`_APPLICATION_WORKFLOW_FILES`/`_APPLICATION_ANCHOR_WORKFLOW`/`_WORKFLOW_DISPLAY_NAMES`/`_CI_STATUS_PER_PAGE` module-level routing logic at `src/hrb_chatbot/api/admin/manage_admin.py` lines ~244-654. Route-level test behavior ported from `tests/hrb_chatbot/api/admin/test_manage_admin.py`'s golden-dataset/eval-runs/ci-status/pipeline blocks, using the same `FakeGoldenDatasetStore`/`FakeEvalRunStore`/`FakePipelineRunStore`/`_FakeGitHubActionsClient` shapes from that repo's `tests/conftest.py` (lines 789-885) and `test_manage_admin.py` itself (lines 538-582).
    - **API surface:** `src/platform/build_deployment/models.py` - `Application` enum (ported as-is, all 4 members) plus the 13 response models listed above, ported as-is. `src/platform/build_deployment/stores.py` - `GoldenDatasetStore`, `EvalRunStore`, `PipelineRunStore`, same CRUD/SQL as the originals (one file, not three - no cross-file coupling between them, just colocated since all three are small). `src/platform/build_deployment/routes.py` - `APIRouter` with the 7 routes (`GET /golden-dataset`, `GET /eval-runs`, `GET /eval-runs/{run_id}`, `GET /ci-status`, `GET /ci-status/pipeline`, `GET /ci-status/pipeline/history`, `GET /ci-status/pipeline/history/{snapshot_id}`), same paths/shapes/status codes, plus the same `Application`-routing module-level maps/helper. `src/platform/common/error_codes.py` gets 2 more constants (`EVAL_RUN_NOT_FOUND`, `PIPELINE_SNAPSHOT_NOT_FOUND`). `src/platform/main.py` adds this module's router (same `/v1/admin` prefix as interview_qa's).
    - **Connection-plumbing adaptation:** identical swap to Phase 1 - all 3 stores' `_connect()` goes through `hrb_common.db.connection.get_connection()`/`PostgresConnectionConfig` instead of a direct `psycopg.connect()` built from `read_setting()`. SQL/CRUD logic unchanged.
    - **GitHub Actions client swap (the other place real logic changes):** the original builds `GitHubActionsClient` through `hrb_chatbot_v2`'s own `ClientGateway.github_actions(repo=None)`, where `repo=None` means "use this project's own `GITHUB_REPO` env default." `hrb-common-libs`' `GitHubActionsClient` takes `repo` as a required constructor arg with no env-var default (deliberate - a shared library has no one default repo, per its own Phase 10 spec). Adaptation: `_APPLICATION_REPOS` in the ported `routes.py` maps `BACKEND`/`INGESTION_LAMBDA` to the literal string `"rvsree/hrb_chatbot_service"` (the real renamed repo, confirmed from this session's own recent commits) instead of `None`, and a small local `_github_actions_client(repo)` helper builds/caches one `GitHubActionsClient(token=..., repo=repo)` per repo string, replacing `ClientGateway.github_actions()`. No shared gateway class invented for this - a plain per-repo dict cache is all one call site needs, matching `hrb-common-libs`' own Phase 13 precedent for a similarly small local substitution.
    - **Behavior parity:** representative subset of the original's ~20 ci-status/pipeline tests (not all 20 - flagged as a scope narrowing, not a gap: the underlying logic is identical either way). Ported: golden-dataset list; eval-runs list + get + 404; ci-status defaults to backend with both workflows + correct repo; ci-status ingestion_lambda shows only its own workflow; ci-status lms_mcp uses its own repo; ci-status frontend returns the honest message and skips the GitHub call entirely; ci-status pagination `has_more`; ci-status surfaces a GitHub error per-workflow as data; pipeline status stitches workflows + finds the nearest eval gate; pipeline status shows no eval gate when none precedes it; pipeline status is honest-message for frontend; pipeline status skips snapshot persistence for non-backend applications; pipeline snapshot history list + get + 404. Not re-ported (same underlying code path, judged redundant given the above already covers it): the remaining per-field repo/anchor-workflow variations and the explicit-sha test.
    - **Out of scope:** `request-metrics`/`RequestMetricsResponse` (not one of this phase's 7 routes - no pipeline/eval/golden-dataset store needed for it, belongs to its own future phase if ever extracted). No RBAC (same as Phase 1 - these routes accept requests with no identity check, `require_role`/`Role.ADMIN` calls dropped, GET routes' query-param identity dropped).
    - **Open questions:** none blocking - flagged in the delivery note: hardcoding `"rvsree/hrb_chatbot_service"` as the literal default repo (replacing the original's env-var-driven default) is a judgment call, not confirmed with the user.

- [x] **Phase 3 (done) — mcp_catalog extraction.** Port Phase 239's `get_mcp_tool_catalog()`/`discover_mcp_tools()` and the `/mcp-tools` route.
  - **Spec:**
    - **Context:** last of the three admin/platform capabilities. Unlike Phase 1/2, this one genuinely needs the `mcp` extra (`CLAUDE.md`'s 2026-10-21 correction) - a real, live `session.list_tools()` call against a configured MCP server, not Postgres/GitHub.
    - **Source:** `hrb_chatbot_v2`'s `src/hrb_chatbot/ai/rag_pipeline/tools/mcp_tools/__init__.py` (`discover_mcp_tools()`/`get_mcp_tool_catalog()`, lines ~145-171 plus the `MCP_SERVERS`/`_tool_catalog_cache` module state around them), `src/hrb_chatbot/models/admin.py`'s `McpToolSummary`/`McpToolCatalogResponse`, and the 1 route at `src/hrb_chatbot/api/admin/manage_admin.py` line ~824.
    - **API surface:** `src/platform/mcp_catalog/models.py` - `McpToolSummary` (`name`/`description`/`input_schema`/`server_id`), `McpToolCatalogResponse` (`tools`/`error`), ported as-is. `src/platform/mcp_catalog/catalog.py` - `discover_mcp_tools(server_id, url_setting_name) -> list[dict]`, `get_mcp_tool_catalog(force_refresh=False) -> dict`, same in-process-cache/error-as-data/never-raises behavior as the original, same `MCP_SERVERS = {"hrb_lms_mcp": "HRB_LMS_MCP_URL"}` single-entry map. `src/platform/mcp_catalog/routes.py` - `GET /mcp-tools`, same shape/status code. `requirements.txt` gets `mcp` added to the `hrb-common-libs[...]` extras list (currently `[observability,db,ci]`, missing it per `CLAUDE.md`'s correction). `src/platform/main.py` adds this module's router.
    - **MCP client swap (the one place real logic changes):** the original's `discover_mcp_tools()` opens a raw `streamablehttp_client`/`ClientSession` itself and builds each tool dict by hand (`tool.name`/`tool.description`/`tool.inputSchema`). This phase calls `hrb_common.mcp.client.list_mcp_tools(server_url, access_token)` instead (already does the session open/`list_tools()`/close), then remaps each returned dict's `inputSchema` key to `input_schema` and adds `server_id` - `list_mcp_tools()` is server-agnostic by design (Phase 5's own spec) and has no concept of which configured server it's calling, so that tagging stays here, not in `hrb-common-libs`.
    - **Auth scope narrowing (flagged, not silently decided):** the original acquires a real bearer token via `hrb_chatbot_v2`'s own Phase 53 OAuth2 client-credentials flow (`get_access_token()`). This phase does **not** port that flow - out of this phase's explicit scope (not listed among the files to port) and `hrb-common-libs`' own `auth` extra isn't in this repo's `requirements.txt`. Instead, `get_access_token()` here reads an optional static token straight from `HRB_LMS_MCP_ACCESS_TOKEN` (empty/`None` if unset, same as having no token at all) - a deliberate simplification to flag with the user, not a hidden gap: a real deployment of this route would need the same OAuth2 flow Phase 2's GitHub token needs, wired in a later phase.
    - **Behavior parity:** `get_mcp_tool_catalog()`'s cache-hit/force_refresh/error-as-data/multi-server-merge behavior, and the route's never-500s contract, are tested the same way the original would be - with a fake `list_mcp_tools` substituted in (no real MCP server, matching this task's Neon/live-infra constraint, which also covers MCP here). No equivalent unit test exists for this function in `hrb_chatbot_v2` today (same situation as Phase 1/2's stores) - new tests are written, not ported.
    - **Out of scope:** real OAuth2 token acquisition (see above). The keyword-routing wrapper functions in the same source file (`is_leave_balance_query`, `get_leave_balance`, etc.) - business logic belonging to `hrb_rag_retrieval_service`, never part of this phase's scope. The Postgres-backed MCP circuit breaker (`_check_circuit_breaker`/`_record_mcp_outcome`) - same exclusion `hrb-common-libs`' own Phase 5 already made for `hrb_common.mcp.client`, not revisited here.
    - **Open questions:** none blocking - flagged in the delivery note: the auth simplification above, and that `mcp`/`pydantic` versions are pinned (`mcp==1.9.4`/`pydantic==2.13.5`) in `hrb-common-libs` for a known version conflict (Phase 5's own fix there) - this repo's `pydantic` (used directly for its own FastAPI models) must stay compatible with that pin.

- [x] **Phase 4 (done) — mcp_catalog real OAuth2, closing Phase 3's own flagged gap.** 33/33 tests pass (1 new test confirming the real `OAuth2ClientCredentials` wiring; 1 existing test updated to fake `_get_access_token` instead of relying on the old stub's no-network-call behavior). User-directed, 2026-10-21: real OAuth2 wherever it's actually required, never a stubbed/alternate substitute, even when flagged. Phase 3's static-token simplification is exactly that - closing it now rather than leaving it as a standing gap.
  - **Spec:**
    - **Context:** Phase 3 explicitly flagged (not hid) that it read a static `HRB_LMS_MCP_ACCESS_TOKEN` env var instead of the real Phase-53 OAuth2 client-credentials flow, reasoning that the flow wasn't in that phase's file list and `hrb-common-libs`' own `auth` extra wasn't yet a dependency. The user's standing preference, given directly after reviewing that flag: wire the real thing, don't substitute, even when disclosed. The real flow already exists and is already generalized for reuse - `hrb-common-libs`' `auth` extra (`hrb_common.auth.oauth_client.OAuth2ClientCredentials`, built Phase 8 there) is the exact same flow `hrb_chatbot_v2`'s own `common/clients/auth_client/oauth_client.py::get_access_token()` implements, just parameterized instead of hardcoded to one caller.
    - **Source:** `hrb_chatbot_v2`'s `common/clients/auth_client/oauth_client.py::get_access_token()` - real env var names confirmed by reading that file directly: `HRB_LMS_MCP_OAUTH_TOKEN_URL` (default `http://127.0.0.1:8190/oauth/token`), `HRB_LMS_MCP_OAUTH_CLIENT_ID`, `HRB_LMS_MCP_OAUTH_CLIENT_SECRET`. `hrb-common-libs`' `OAuth2ClientCredentials(token_url, client_id, client_secret).get_access_token() -> str` (already built, already tested there - not re-implemented here).
    - **API surface:** `src/platform/mcp_catalog/catalog.py::_get_access_token()` changes from reading a static token to building (lazily, module-level cached) an `OAuth2ClientCredentials` from the 3 env vars above and calling `.get_access_token()` on it - same return type (`str`), same call site (`discover_mcp_tools()`), no change to any other function's signature. `requirements.txt` gains `auth` in the `hrb-common-libs[...]` extras list (was `[observability,db,ci,mcp]`, becomes `[observability,db,ci,mcp,auth]`).
    - **Behavior parity:** when the 3 env vars are unset, `client_id`/`client_secret` resolve to `""` (same empty-string default `hrb_chatbot_v2`'s own version uses) - the real client will attempt a token request and fail/log rather than silently returning `None` the way Phase 3's stub did; this is the REAL system's actual behavior today (confirmed by reading `oauth_client.py`), not a new failure mode introduced here.
    - **Failure modes:** `discover_mcp_tools()`'s existing `except Exception` handling in `get_mcp_tool_catalog()` already treats any failure (now including a real OAuth2 token-request failure) as error-as-data for that one server - unchanged, no new exception handling needed.
    - **Out of scope:** no change to `hrb-common-libs`' own `auth` extra - consumed as-is. No change to `hrb_chatbot_v2`'s own OAuth2 implementation - read-only source.
    - **Open questions:** none blocking.

  - **Real incident during this phase, 2026-10-23:** while diagnosing an unrelated `CREATE_FAILED` (see below), a debug command printed the real Neon `POSTGRES_DB_PASSWORD` value into the session transcript in plaintext. Rotated immediately afterward (new 32-char password set directly via `ALTER ROLE`, both the `hrb-chatbot/POSTGRES_DB_PASSWORD`-prefixed and unprefixed Secrets Manager entries updated, `hrb_chatbot_service`'s own App Runner service redeployed to pick up the new value) - confirmed via its live `/health` endpoint reporting the Postgres-backed metadata store healthy again. No other secret was exposed.
  - **CREATE_FAILED red herring:** the App Runner service failed to create twice in a row the instant any `RuntimeEnvironmentSecrets` entry was present, with zero application logs either time, even though the instance role's `secretsmanager:GetSecretValue` permission checked out via `iam simulate-principal-policy`. Isolated by testing with zero secrets (succeeded), one old-style secret (failed), then one freshly-exercised secret (`GITHUB_TOKEN`, succeeded) - the full 8-secret config then succeeded cleanly once enough time had passed since the secrets/roles were first created. Conclusion: IAM/Secrets Manager propagation delay immediately after creating new roles/secrets, not a real configuration bug - noted here so a future same-day redeploy right after provisioning doesn't get mistaken for a logic error.
